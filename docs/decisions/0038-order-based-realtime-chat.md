# ADR-0038：基于订单的实时聊天 MVP

- 状态：已接受
- 日期：2026-11-10
- 决策人：项目负责人

## 背景

- `[PRD]` 聊天能力围绕预约订单履约，不建设任意用户之间的开放私聊。
- `[PRD]` 聊天记录至少保留 180 天。
- `[CONFIRM]` 订单完成后的发送窗口原 PRD 未明确；本次按项目讨论采用完成后 7 天。

## 决策

- `[DESIGN]` 使用 Django Channels、WebSocket 和 Redis Channel Layer 实现实时转发，不接入第三方 IM。
- `[DESIGN]` PostgreSQL 的订单会话、成员、消息和已读位置是最终事实；Redis 只保存实时广播状态，不保存消息事实。
- `[DESIGN]` 一个订单只创建一个双方会话；会话成员由订单预约用户和服务者决定，客户端不能自行指定聊天对象。
- `[DESIGN]` WebSocket 使用 60 秒级、一次性、哈希保存的连接票据，URL 不保存长期 Access Token；连接后每个订阅仍校验会话成员身份。
- `[DESIGN]` 客户端发送消息必须携带 `client_message_id`，服务端在同一会话、同一发送者范围内幂等；同标识不同内容返回冲突。
- `[DESIGN]` 消息 `sequence` 在订单会话内严格递增，支持历史分页、断线补偿、已读位置和未读统计。
- `[DESIGN]` 消息创建与 MessageDelivery Outbox 同事务保存；Redis 故障不回滚消息，后台任务负责幂等重试。
- `[DESIGN]` 支持 `TEXT`、`IMAGE`、`SYSTEM`；图片必须是发送者本人上传且用途为 `CHAT_IMAGE` 的媒体。
- `[DESIGN]` 待支付订单不开放会话；取消和退款订单只读；完成后 7 天内可发送，之后只读，但消息继续按合规期限留存。
- `[DESIGN]` 订单支付成功落账事务内幂等创建订单会话、预约用户和服务者成员，以及一条 `SYSTEM` 支付成功提示；服务者接单不是聊天开放前置条件。
- `[DESIGN]` 支付成功提示使用 `system:order-paid:<order_no>` 作为系统幂等标识，并由数据库约束保证余额支付、外部支付回调和历史补齐不会重复生成。
- `[DESIGN]` 历史已支付订单通过幂等管理命令补齐，支持 `--dry-run` 预检；当前开发库已按项目负责人要求补齐，其他环境写入前必须确认数据范围。

## 备选方案

- 第三方 IM：接入快但增加身份映射、费用、数据导出、合规和供应商锁定，本期不采用。
- 仅轮询 REST：实现简单但实时性和连接效率不足，保留 REST 作为历史、补偿和降级通道。
- Redis 直接保存消息：吞吐高但不是可靠资金级业务事实，不作为最终消息存储。

## 影响

- Web 进程需要通过 Daphne 或兼容 ASGI 服务启动，才能同时处理 HTTP 和 WebSocket。
- Redis Channel Layer 成为实时推送依赖；Redis 不可用时 REST 发送仍保存消息，并由 Outbox 重试补发。
- API 增加订单会话、消息历史、发送、已读、未读汇总和 WebSocket 票据接口。
- 聊天图片复用媒体上传能力，但增加 `CHAT_IMAGE` 专用用途，避免引用头像、生活照或服务图片。
- 支付成功后双方无需手动创建会话，订单会话会出现在双方 `GET /api/v1/conversations/`，`last_message` 为支付成功系统提示并进入未读统计。

## 风险与缓解

- 消息重复：使用客户端幂等标识、请求摘要和数据库唯一约束。
- 乱序和断线：使用会话内严格序号、`after_sequence` 补偿和游标历史接口。
- Redis 故障：PostgreSQL 先落库，MessageDelivery Outbox 后续重试，不丢失消息事实。
- 越权读取：HTTP 和 WebSocket 每次订阅都校验订单会话成员；非成员不返回会话存在性。
- 敏感内容泄露：日志不记录消息正文、票据明文或完整联系信息。
- 系统消息重复：使用确定性 `client_message_id`、发送者为空的专用唯一约束和会话行锁。
- 历史数据缺口：提供只读预检和幂等补齐命令，避免直接修改聊天消息表。

## 验证

- 覆盖订单权限、支付成功双方会话与系统提示、未支付/取消/退款/完成窗口、重复初始化、幂等冲突、已读单调性、图片归属和 WebSocket 票据复用。
- 运行 Django check、迁移、pytest、Ruff 和 OpenAPI 生成。
