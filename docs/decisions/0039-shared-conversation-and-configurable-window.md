# ADR-0039：用户—服务者共享会话与配置化发送窗口

- 状态：已接受
- 日期：2026-11-11
- 决策人：项目负责人

## 背景

- `[PRD]` 聊天只允许发生在已有预约订单关系的普通用户与服务者之间。
- 原实现按订单创建会话，同一用户与服务者重复下单会产生多个聊天入口，历史消息分散，不符合已确认的会话管理预期。
- `[CONFIRM]` 已确认同一用户与服务者只保留一个共享会话，多个订单复用；会话可由当前用户隐藏，后续存在订单关系时仍可恢复。订单完成后的发送窗口需要可配置，当前默认 7 天。

## 决策

- `[DESIGN]` 以“预约用户 + 服务者”为会话唯一边界，使用稳定 `pair_key` 和数据库唯一约束保证只有一个规范共享会话。
- `[DESIGN]` `Conversation.order` 仅作为历史兼容的首个订单锚点；通过 `ConversationOrderLink` 记录共享会话与多个订单的来源关系。
- `[DESIGN]` 最新有效订单决定会话的可发送状态；待支付订单不形成聊天资格，取消、退款、完成超窗只改变发送状态。
- `[DESIGN]` 完成订单后的发送窗口读取 `MESSAGING_COMPLETED_SEND_WINDOW_DAYS`，默认值为 7；生产启用值仍需业务负责人确认。
- `[DESIGN]` 会话删除采用 `ConversationMember.hidden_at` 的用户级隐藏，不删除消息；新订单支付成功或用户从服务者入口打开会话时恢复可见。
- `[DESIGN]` 旧的按订单重复会话通过兼容合并逻辑迁移消息和订单关联，不删除历史消息、订单或审计事实。

## 备选方案

- 每个订单继续创建独立会话：实现简单，但同一双方聊天入口重复、历史割裂，不符合已确认需求。
- 只保留最新订单会话并删除旧会话：会丢失消息和订单来源，违反聊天留存和可追溯要求。
- 引入独立 IM 平台：当前仅需订单关系聊天，基础设施和成本过重，继续使用模块化单体内的 WebSocket、PostgreSQL 事实数据和 Outbox。

## 影响

- 会话详情新增 `orders/order_count`，最新订单继续通过 `order` 返回。
- 新增按服务者打开/恢复共享会话接口，以及当前用户隐藏会话接口。
- 支付成功、历史订单补齐和新订单复用共享会话时必须幂等追加订单关联和系统提示。
- 数据库新增配对唯一键、订单关联表和成员隐藏时间，并提供可重复执行的兼容合并逻辑。

## 风险与缓解

- 旧重复会话合并失败可能造成消息归属不一致：合并过程在事务中执行并通过订单关联唯一约束防重，保留旧会话和消息事实。
- 多订单并发创建可能竞争同一会话：使用 `pair_key` 唯一约束和 `get_or_create` 冲突恢复处理。
- 配置化窗口可能被误配为过短或过长：启动测试和配置文档固定默认值，生产值变更需单独审批并记录。
- 用户级隐藏可能被误解为物理删除：API 和文档明确只影响可见性，不清理聊天记录。

## 验证

- 自动化测试覆盖多订单复用、最新订单状态、支付提示幂等、配置化窗口、隐藏/恢复和配对唯一约束。
- 运行迁移检查、全量测试、Ruff 检查和 OpenAPI 生成，确认接口文档包含新增路由和响应模型。
