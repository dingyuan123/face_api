# ADR-0004：Celery + Redis 配合 Outbox/Inbox

- 状态：提议（待技术负责人确认）
- 日期：2026-10-27
- 决策人：待技术负责人确认 `[CONFIRM]`

## 背景

PRD 有支付回调补偿、通知、索引、超时、结算、奖励和对账等异步任务，并要求重复任务不重复处理。

## 决策

- `[DESIGN]` 使用 Celery worker/beat，Redis 作为初始 broker/result 辅助。
- `[DESIGN]` 业务事务内写 Outbox；Celery 只负责投递，消费者写 Inbox 并按 `event_id + consumer_name` 幂等。
- `[DESIGN]` Redis 锁用于减少重复任务，不作为事件、状态或资金的最终事实。
- `[DESIGN]` 任务必须重试策略、死信、告警、执行记录、人工重放和回滚/补偿接口。

## 备选方案

- RabbitMQ/Kafka：可靠性和吞吐更强，但当前增加运维和开发成本；达到明确规模后再评估。
- 同步调用第三方：简单但失败会阻塞交易，且无法可靠补偿。

## 影响

- 交易事务和异步副作用解耦；事件乱序、重复和第三方失败需要显式处理。
- 任务监控、版本化事件和数据留存成为基础要求。

## 风险与缓解

- 风险：内存信号丢失。缓解：Outbox；风险：重复消费。缓解：Inbox 唯一约束；风险：任务积压。缓解：指标、限速和死信。

## 验证

- 重复事件、乱序事件、任务失败/重试/重放、Outbox 提交崩溃恢复和定时任务并发测试。
