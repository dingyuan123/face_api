# ADR-0001：采用模块化单体

- 状态：提议（待项目负责人确认）
- 日期：2026-10-27
- 决策人：待项目负责人确认 `[CONFIRM]`

## 背景

PRD 覆盖用户、认证、服务、订单、支付、资金、奖励、IM、内容、安全和运营。第一阶段团队和业务规模不需要微服务集群，但模块边界混乱会导致资金和权限风险。

## 决策

- `[DESIGN]` 使用 Django/DRF 模块化单体，业务模块独立迁移、服务、查询、事件和测试。
- `[DESIGN]` 模块通过公开服务、查询和领域事件协作；禁止跨模块直接修改内部表。
- `[DESIGN]` 第一阶段不建设微服务、Kubernetes、Kafka、独立规则引擎。

## 备选方案

- 微服务：隔离强，但引入分布式事务、部署、观测和团队成本，当前不必要。
- 单一扁平应用：启动快，但订单/资金/权限边界不清，长期维护风险更高。

## 影响

- 可在一个数据库事务内保护订单、支付结果、快照和 Outbox。
- 模块可按阶段独立测试和演进；未来可在明确容量或组织边界后拆出服务。

## 风险与缓解

- 风险：模块互相 import。缓解：依赖检查、公开契约、ADR 和测试。
- 风险：业务逻辑堆在视图。缓解：应用服务/领域服务规范和代码评审。

## 验证

- 静态检查依赖方向；模块契约测试；资金/订单事务测试。
