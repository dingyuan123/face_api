# ADR-0031：PostgreSQL 综合搜索、搜索聚合和热门搜索控制

- 状态：已接受
- 日期：2026-11-06
- 决策人：项目负责人（本次“开始实施”确认）

## 背景

前端需要一次性搜索服务者、动态和资讯，并展示“大家都在搜”。当前业务规模、部署方式和运维能力不足以证明需要独立搜索引擎；但搜索又必须具备公开数据隔离、稳定排序、隐私保护和人工运营能力。

## 决策

- `[DESIGN]` 首期通过 PostgreSQL 查询实现服务者、动态、资讯综合搜索和分类分页，不引入 Elasticsearch/Meilisearch。
- `[DESIGN]` 搜索查询按公开可见性筛选，服务者、动态、资讯只复用各自公开查询投影，不从管理端或内部服务读取敏感字段。
- `[DESIGN]` 搜索词统一规范化；有效公开搜索只按自然日聚合次数，不保存用户 ID、设备、IP、精确时间或原始搜索记录。
- `[DESIGN]` 敏感搜索词在统计和人工热门配置入口过滤；“大家都在搜”由自动聚合与管理员人工控制合并。
- `[DESIGN]` 自动热门词按配置窗口和公式计算；管理员支持人工置顶、展示、下线和屏蔽，修改使用 `expected_version` 乐观锁。
- `[DESIGN]` 搜索结果响应保持稳定 API 合约；未来如迁移搜索引擎，只替换查询/索引适配层，不改变客户端接口。

## 备选方案

- Elasticsearch/Meilisearch：搜索能力和扩展性更强，但当前增加部署、数据同步、一致性和运维成本。
- 只做各模块独立搜索：实现简单，但前端无法完成统一搜索页和统一热门词。
- 保存完整搜索行为再计算热度：指标更丰富，但增加隐私、合规、留存和反作弊成本。

## 影响

- 新增 `search_query_stats` 和 `search_trending_keywords` 两张聚合/配置表。
- 新增公开综合搜索、分类搜索、热门搜索和管理员热门配置接口。
- 搜索质量、延迟和容量需要持续测量，为后续独立搜索引擎决策提供数据。

## 风险与缓解

- 风险：数据库模糊查询在数据规模增长后延迟上升。缓解：限定公开数据集、监控慢查询、建立索引投影，并保留搜索适配边界。
- 风险：简单关键词匹配的召回和相关性不足。缓解：后续评估 PostgreSQL 全文检索、分词、拼音、纠错，不在首期过度实现。
- 风险：热门词泄露敏感意图。缓解：敏感词前置过滤、屏蔽状态、人工审核和不保存原始搜索记录。
- 风险：自动热度并发累加重复。缓解：按自然日和规范化词唯一约束，并在事务冲突后幂等补偿。

## 验证

- 验证综合搜索命中服务者、动态和资讯且只返回公开数据。
- 验证分类分页、搜索词规范化、敏感词过滤、每日聚合唯一性和并发累加。
- 验证热门排序、人工置顶、展示/下线/屏蔽、幂等创建和版本冲突。
- 验证数据库迁移、中文备注、OpenAPI 合约、权限、异常和重复请求测试。
