# ADR-0041：一级邀请绑定与推广奖励账本

- 状态：已接受
- 日期：2026-11-12
- 决策人：项目负责人

## 背景

- `[PRD]` 新用户通过邀请码、链接或海报注册后绑定唯一一级直接邀请人，被邀请人产生有效订单后邀请人获得动态比例奖励。
- 邀请关系必须防止自邀请、老用户补绑和同设备批量注册套取奖励；奖励必须可处理支付、退款、结算、提现和对账。

## 决策

- `[DESIGN]` 服务端生成用户唯一邀请码，分享链接携带 `invite_code/share_no/channel/campaign_code`，客户端不能提交邀请人内部用户 ID。
- `[DESIGN]` 手机号首次注册在账号创建事务中绑定归因；OAuth 用户在完成手机号绑定时归因，合并到已有账号不补绑。老用户永久不补绑。
- `[DESIGN]` 被邀请用户建立数据库唯一归因；同值重复幂等，异值冲突不覆盖。同设备多归因标记风险待复核，不直接删除关系。
- `[DESIGN]` 匿名分享访问只保存 HMAC 摘要并按配置清理；分享次数、访问次数和注册转化分开统计。
- `[DESIGN]` 政策为不可变版本，订单支付时锁定政策和比例；奖励按整数分向下取整，可受单笔上限和订单平台服务费资金上限约束。
- `[DESIGN]` 订单完成生成唯一奖励，经过可配置观察期后写入 `REFERRAL_REWARD` 收益账户。退款生成调整流水；已结算奖励自动追回，余额不足转人工处理。
- `[DESIGN]` 所有人工冻结、解冻、取消和金额调整使用 `expected_version`、原因、幂等键和状态审计。

## 备选方案

- 允许老用户事后绑定邀请人：容易被刷单和抢归因，不符合“新用户注册绑定”语义。
- 在用户表直接保存可覆盖的邀请人字段：难以保留冲突、风险和历史审计，故使用唯一归因表。
- 支付成功立即发奖励：退款和风险观察期会造成大量追回，故支付只建快照，完成后延迟结算。
- 用 Redis 保存奖励状态：无法满足资金可追溯和事务一致性，奖励和流水继续以 PostgreSQL 为事实来源。

## 影响

- 登录、Apple 登录、微信登录和手机号绑定请求支持 `referral_context`。
- 新增分享赚钱总览、分享链接、访问记录、奖励明细和管理员政策/奖励接口。
- 订单支付、完成和退款服务接入奖励快照与调整；推广收益复用现有收益账户和提现能力。

## 风险与缓解

- 正式奖励比例未配置时默认 0，不产生奖励；管理员必须先创建政策版本。
- 平台服务费资金上限、奖励税费和已提现追缴仍需财务确认；自动冲减只处理可用余额，不足进入人工追缴。
- 同设备风险规则可能误报，只冻结奖励资格并保留人工复核，不直接删除归因。
- 分享访问摘要仍属于隐私数据，按配置保留期清理且不记录明文设备/IP。

## 验证

- 自动化测试覆盖绑定、归因冲突、分享转化、奖励快照、结算、退款冲减、人工调整和唯一约束。
- 运行迁移检查、完整 pytest、Ruff、OpenAPI 和管理命令检查。
