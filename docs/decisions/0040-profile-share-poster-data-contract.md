# ADR-0040：个人分享海报数据契约

- 状态：已接受
- 日期：2026-11-12
- 决策人：项目负责人

## 背景

- `[PRD]` 分享赚钱页需要生成邀请海报，海报包含品牌文案、用户公开资料、主页二维码和分享链接。
- 前端负责海报排版和图片绘制，需要后端提供稳定字段，不希望在客户端硬编码品牌文案或拼接个人资料。
- 分享内容不得泄露手机号、证件、访问令牌或内部用户 ID。

## 决策

- `[DESIGN]` 新增 `GET /api/v1/users/me/share-poster/`，只允许登录用户读取自己的海报数据。
- `[DESIGN]` 海报品牌文案通过 `SHARE_POSTER_*` 环境变量配置；接口返回当前配置值，便于运营调整而不要求客户端发版。
- `[DESIGN]` 个人昵称、年龄、城市、签名和兴趣标签来自个人资料；未填写年龄返回 `null`，兴趣标签返回展示名称。
- `[DESIGN]` `cover` 复用 `MediaAssetSummary`，本期使用个人头像作为主视觉，未上传时为空并由前端使用占位图。
- `[DESIGN]` `profile_url` 使用 `PUBLIC_SHARE_BASE_URL/invite/`；后端托管前端提交的 H5 邀请落地页，不包含访问令牌。短链效果通过配置较短分享域名实现，本期不建设短链表和跳转服务。
- `[DESIGN]` `qr_image_url` 由后端生成二维码 PNG 并返回短期签名地址，二维码内容编码 `profile_url`；前端直接渲染图片，不需要引入二维码库。
- `[DESIGN]` 二维码图片保存在本地媒体目录并按分享链接复用；地址带 HMAC 签名和过期时间，过期后重新请求海报接口刷新。
- `[DESIGN]` 扫码落地优先走 App Universal Link/Deep Link；微信/浏览器无法唤起 App 时使用轻量 H5 落地页传递 `invite_code/share_no`，服务端只在登录注册时绑定关系。
- `[DESIGN]` `share.link_url` 与 `profile_url` 一致，`share.title/description` 为后续微信分享卡片预留字段。

## 备选方案

- 服务端直接生成海报图片：前端无法灵活适配多语言、字体和屏幕，且增加图片存储、模板版本和缓存清理。
- 服务端生成二维码图片：会引入依赖、静态文件生命周期和访问签名问题；当前链接可由前端直接编码，成本更低。
- 建设短链数据库和统计跳转：会引入公开重定向、风控、归因和隐私问题；当前需求只用于二维码和复制链接，暂不需要。

## 影响

- OpenAPI 中提供完整海报响应模型和中文字段说明。
- `PUBLIC_SHARE_BASE_URL` 同时用于资讯与用户主页分享，生产必须配置真实 HTTPS 域名。
- 前端直接加载 `qr_image_url`，并保留 `cover=null` 时的本地占位图；如需覆盖微信扫码场景，需要配套 H5 落地/跳转页。

## 风险与缓解

- 公开主页链接包含用户公开 UUID：链接只在用户主动分享时展示，不包含令牌和敏感身份字段；未来主页仍需独立审核公开字段。
- 配置文案可能被误当正式规则：文档标记当前值为默认配置，正式文案继续保留待确认项。
- 头像尺寸可能不适合海报：接口返回原始宽高，前端负责裁切；后续可增加专用海报封面媒体用途。

## 验证

- 自动化测试覆盖完整数据、默认数据、认证、安全域名和敏感字段不泄露。
- OpenAPI、Ruff、迁移检查和完整 pytest 回归必须通过。
